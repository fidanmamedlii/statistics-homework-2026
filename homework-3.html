01 / ECC HYBRID ENCRYPTION

The curve helps the two sides agree on a secret

Elliptic-curve multiplication creates public points and lets two sides calculate the same shared point. AES-GCM does the actual message encryption. This is a hybrid design: public-key mathematics establishes a symmetric key; a symmetric cipher handles the message bytes.

1
Receiver: choose private d, publish Q = dGd stays secret. G and Q are public. In this classroom demo, d is intentionally limited to 1–64.
2
Sender: choose one-time r; send R = rGR is an ephemeral public point sent with the ciphertext. A real system uses a fresh, securely random r from the full valid range.
3
Sender computes S = rQ; receiver computes S = dRBoth equal drG. An observer sees Q and R but should not be able to calculate the shared point without a private scalar.
4
HKDF-SHA-256(x(S), salt, context) → AES keyAES-256-GCM encrypts UTF-8 bytes using that key and a fresh 96-bit random nonce. The 128-bit tag detects modification. The receiver computes dR, derives the same key, and verifies the tag before accepting plaintext. Q and R are bound as authenticated additional data; this does not authenticate a person's identity.
Do not reuse these demo keys. The curve arithmetic is written here for learning and is not constant-time or audited. The small private-key range makes the system deliberately breakable. Never put a real wallet key, mnemonic, or private message into a toy cryptography demo.

A QUICK COMPARISON

What the output reveals

Caesar is a monoalphabetic substitution: every A becomes the same shifted letter, every B becomes another, and so on. It preserves the exact shape of the letter-frequency histogram, only relabelling the bars.

The ECC page displays ciphertext bytes as hexadecimal. AES-GCM is designed to make ciphertext bytes look pseudorandom and also authenticates them; counting hex characters in a short sample is not a meaningful security test. Statistical appearance alone never proves security.

Letter entropy H = −Σp log₂p describes observed A–Z counts. The index of coincidence Σnᵢ(nᵢ−1)/(N(N−1)) estimates how often two letters drawn without replacement match. Caesar preserves both. AES statistics use bytes: their maximum entropy is 8 bits/byte, while A–Z has a maximum of log₂26 ≈ 4.70 bits/letter. These different alphabets must not be compared as security scores. Short samples are biased and variable.

With a fixed shift, repeated plaintext gives identical Caesar output. Fresh salt and nonce normally change the ECC demo's encrypted output even if d and r are left unchanged. The manually chosen r remains insecure; real schemes require appropriate fresh randomness.

03 / STATISTICAL CRYPTANALYSIS

Compare exhaustive search, letter frequencies, and n-grams

The code estimates letter probabilities from a known-language training corpus. For each possible Caesar key, it decrypts the ciphertext and calculates a chi-squared score against those probabilities. The lowest score is the best statistical guess. A short text may not contain enough letters for its frequencies to resemble the language.

Exactly how the two statistical scores are calculated

Letter model: pᵢ = (cᵢ + 0.5)/(N + 13), where cᵢ is the corpus count and N is its total A–Z letters. Adding 0.5 avoids zero expected counts. For a candidate of length L, Eᵢ = Lpᵢ and χ² = Σ(Oᵢ−Eᵢ)²/Eᵢ. The lowest score ranks first. This is a ranking heuristic; no hypothesis-test p-value is claimed for sparse short texts.

N-grams: count overlapping pairs and triples in the normalized corpus. Spaces are removed, so sequences may cross word boundaries. For order n, p(g) = (count(g)+0.5)/(total n-grams+0.5×26ⁿ). Score each candidate with the mean log probability of its bigrams plus the mean log probability of its trigrams. Higher is better. Two-letter candidates use bigrams only; shorter candidates have no n-gram score. Ties use the smaller shift. This is a character-sequence scoring heuristic, not a calibrated sentence probability. The n-gram model uses more context, but unseen sequences, smoothing, a small corpus, and mismatched subject matter can still cause mistakes.

Neither score is a probability that a key is correct. Compare candidates for the same ciphertext and model; do not interpret raw scores from different lengths or corpora as comparable confidence levels.

Optional attack comparison

  • Exhaustive Caesar search: decrypt with every shift and inspect the 26 outputs. It always includes the correct key; a person or score must select the readable one.
  • Single-letter frequency / chi-square: score all shifts against a language corpus. It is easy to implement and often works on longer text, but can mis-rank short samples.
  • Bigram and trigram scoring (implemented above): use letter order as well as counts. Both models are learned from the same editable corpus and compared on the same held-out windows. They require more training material and can still rank the wrong key first.
  • ECC restricted-key search: test candidate private scalars against Q. It is not a language-statistics attack: the public-key equation provides a direct candidate check.

CONCLUSION

What the experiment can—and cannot—tell us

The experiments show that recoverability depends on the design and the size of the secret search space. Caesar fails because it has only 26 shifts and preserves plaintext statistics. The ECC demonstration fails because we intentionally shrink the private-key choices to 64; matching a candidate public point then recovers the key. With the full secp256k1 group, the same enumeration idea has an astronomical search space.

Neither a successful demo nor a uniform-looking chart proves real cryptographic security. Real systems need vetted algorithms, strong randomness, safe key derivation, correct nonce handling, side-channel-resistant implementations, and independent review.

OPTIONAL / ALTERNATIVE ECC ATTACKS AND DESIGN ANALYSIS

Separate a small key space from a weak implementation

Exhaustive search, implemented: compute G, 2G, 3G, …, BG by adding G each time, and compare with Q. At most B candidates are checked. For a uniformly chosen d in 1…B, the average is (B+1)/2 checks; d=37 takes 37. Each match is exact, independent of the message language.

Baby-step giant-step, implemented: store jG for 0 ≤ j < m, with m=ceil(√(B+1)). Compare Q−imG with that table. A match gives d=im+j within 1…B. Search and storage scale as O(√B), trading memory for work. With B=64, this implementation stores 9 points. Setup matters at small bounds; it need not beat a lucky early exhaustive match.

Attack the temporary scalar, implemented: replace Q by R in either search. Recovering r allows S=rQ and decryption without recovering the receiver's d. Thus a full-size receiver key would not rescue a scheme whose ephemeral r is restricted to 64 choices. This is a second instance of the same small-search-space weakness.

Other alternatives, discussed: Pollard's rho solves a generic discrete logarithm with expected O(√n) work and much less storage than BSGS. Pollard's kangaroo targets a known interval in roughly square-root interval work; see Pollard's original paper. For full-size secp256k1, generic classical attacks are on the scale of 2¹²⁸ group operations, still infeasible. About 2²⁵⁶ possible private scalars does not mean 256-bit security against every attack. These asymptotic comparisons are explained in the Handbook of Applied Cryptography, chapter 3.
