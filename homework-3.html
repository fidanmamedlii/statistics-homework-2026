01 / ECC HYBRID ENCRYPTION

The curve helps the two sides agree on a secret

Elliptic-curve multiplication creates public points and lets two sides calculate the same shared point. AES-GCM does the actual message encryption. This is a hybrid design: public-key mathematics establishes a symmetric key; a symmetric cipher handles the message bytes.

1
Receiver: choose private d, publish Q = dGd stays secret. G and Q are public. In this classroom demo, d is intentionally limited to 1–64.
2
Sender: choose one-time r; send R = rGR is an ephemeral public point sent with the ciphertext. A real system uses a fresh, securely random r from the full valid range.
3
Sender computes S = rQ; receiver computes S = dRBoth equal drG. An observer sees Q and R but should not be able to calculate the shared point without a private scalar.
4
HKDF-SHA-256(S) → AES key; AES-GCM encrypts the messageThe sender transmits R, a salt, a unique nonce, and authenticated ciphertext. The receiver repeats the key derivation and decrypts.
Do not reuse these demo keys. The curve arithmetic is written here for learning and is not constant-time or audited. The small private-key range makes the system deliberately breakable. Never put a real wallet key, mnemonic, or private message into a toy cryptography demo.

02 / CAESAR CIPHER

A QUICK COMPARISON

What the output reveals

Caesar is a monoalphabetic substitution: every A becomes the same shifted letter, every B becomes another, and so on. It preserves the exact shape of the letter-frequency histogram, only relabelling the bars.

The ECC page displays ciphertext bytes as hexadecimal. AES-GCM is designed to make ciphertext bytes look pseudorandom and also authenticates them; counting hex characters in a short sample is not a meaningful security test. Statistical appearance alone never proves security.

03 / STATISTICAL CRYPTANALYSIS

Use a language corpus to rank the 26 shifts

The code estimates letter probabilities from a known-language training corpus. For each possible Caesar key, it decrypts the ciphertext and calculates a chi-squared score against those probabilities. The lowest score is the best statistical guess. A short text may not contain enough letters for its frequencies to resemble the language.

Observed default run: the 6,655-letter built-in corpus was compared with a separate sample encrypted using shift 7. The first prefixes of 5, 10, 20, and 40 letters chose the wrong shift; prefixes of 80, 160, 320, 640, and 1,000 letters chose shift 7. This is one controlled example, not a universal minimum length. A chi-square score is useful for ranking shifts for the same ciphertext; its raw values should not be compared across different message lengths.

Interpretation: a Caesar shift preserves language patterns, so enough ciphertext letters can reveal the shift. The chi-square result is a ranking, not a proof: short texts, names, technical vocabulary, mixed languages, unusual spelling, or a mismatched corpus can make the wrong shift score best.

Optional attack comparison

  • Exhaustive Caesar search: decrypt with every shift and inspect the 26 outputs. It always includes the correct key; a person or score must select the readable one.
  • Single-letter frequency / chi-square: score all shifts against a language corpus. It is easy to implement and often works on longer text, but can mis-rank short samples.
  • Bigram or trigram scoring: compare pairs or triples such as common letter sequences. It uses more language information and can improve short-text guesses, but needs a larger n-gram model and still does not guarantee success.
  • ECC restricted-key search: test candidate private scalars against Q. It is not a language-statistics attack: the public-key equation provides a direct candidate check.
KEY-SPACE SCALE64 demo keys → 2²⁵⁶ real candidates

Even an imaginary rate of 10¹² full candidate checks each second would take about 3.7 × 10⁵⁷ years to scan 2²⁵⁶ candidates. This is a scale illustration, not a benchmark.

CONCLUSION

What the experiment can—and cannot—tell us

The experiments show that recoverability depends on the design and the size of the secret search space. Caesar fails because it has only 26 shifts and preserves plaintext statistics. The ECC demonstration fails because we intentionally shrink the private-key choices to 64; matching a candidate public point then recovers the key. With the full secp256k1 group, the same enumeration idea has an astronomical search space.

Neither a successful demo nor a uniform-looking chart proves real cryptographic security. Real systems need vetted algorithms, strong randomness, safe key derivation, correct nonce handling, side-channel-resistant implementations, and independent review.
