01 / HUMAN-READABLE BACKUP

BIP-39 · mnemonic and seed

BIP-39 turns randomly generated entropy plus a checksum into words chosen from a fixed word list. A valid sentence encodes 128–256 bits of entropy: the checksum is one bit per 32 bits of entropy, and the combined bits are split into 11-bit word indexes. The mnemonic and optional passphrase are fed into PBKDF2-HMAC-SHA512 with 2,048 iterations to produce a 512-bit seed (the salt begins with the literal word mnemonic).

The words are an encoding of entropy and a checksum; the seed is the binary output used by HD-wallet derivation. A BIP-39 passphrase changes the resulting seed, so a forgotten passphrase cannot be recovered from the words alone.

02 / TREE OF KEYS

BIP-32 · hierarchical derivation

BIP-32 uses HMAC-SHA512 with the key Bitcoin seed to turn the seed into a master extended private key and chain code. A derivation path selects child keys below that master. Extended public keys can derive non-hardened public children without exposing private keys; hardened derivation requires private-side material and creates a boundary in the tree.

This is deterministic key derivation: the same seed and path reproduce the same key. It is distinct from key generation, where secure randomness first creates the root entropy or secret.

03 / ACCOUNT PATH

BIP-44 · path convention

BIP-44 specifies a multi-account hierarchy with five path levels:

m / purpose' / coin_type' / account' / change / address_index

For a commonly used Ethereum external account, the path is m/44'/60'/0'/0/0. The apostrophe marks a hardened level. Coin type 60 is registered for Ether in SLIP-44. BIP-44 organizes keys; it does not define the elliptic-curve math or address hash.

04 / PUBLIC KEY AND SIGNATURE

secp256k1 · elliptic-curve cryptography

Ethereum externally owned accounts use ECDSA over secp256k1. A private scalar d generates public point Q = dG on the specified curve. The private key signs; a verifier uses the public key to check the signature.

Calculating Q from d is efficient. Given a public point and the standard generator, finding d is the elliptic-curve discrete logarithm problem. Curve multiplication creates a public key; it is neither a hash nor a checksum.

05 / FIXED-LENGTH DIGEST

Keccak-256 · Ethereum hashing

The Ethereum address is derived by hashing the public key (the 64-byte x and y coordinates, without the uncompressed-key prefix) with Keccak-256, then taking the last 20 bytes. This gives a 160-bit address with a 40-character hexadecimal representation plus 0x.

A cryptographic hash maps arbitrary-length input to a fixed-length digest. The address is not the public key and cannot be used to reconstruct it. Hashing here does not sign or encrypt the key.

Keccak-256 is not SHA3-256. Keccak was selected as SHA-3, but NIST's final FIPS 202 standard uses different domain-separation/padding bits. For the same input, Ethereum's Keccak-256 and standardized SHA3-256 produce different digests.

06 / READABLE CHECK

EIP-55 · mixed-case address

EIP-55 hashes the lowercase hexadecimal address text with Keccak-256. It uses the resulting hash nibbles to decide which address letters are upper-case. The capitalization pattern allows software and people to detect many accidental typing errors while leaving the address value and length unchanged.

It is an encoding checksum, not a secret key, digital signature, identity proof, or defense against a malicious address substitution. EIP-55 estimates about 15 check bits on average; the stated probability of a random mistype accidentally passing is 0.0247%.

WHY EACH TOOL IS DIFFERENT

Six jobs in the pipeline

  • BIP-39, BIP-32, and BIP-44 manage and derive keys: BIP-39 encodes entropy and generates a seed; BIP-32 creates a reproducible tree of child keys; BIP-44 gives the tree a standard account and coin path.
  • secp256k1 supplies the public/private relationship: derive a public point from a private scalar and support digital signatures.
  • Keccak-256 supplies a digest: map public-key bytes to a fixed-size output, from whose final 20 bytes the address is formed.
  • EIP-55 supplies a checksum representation: vary letter case deterministically so many transcription mistakes are detectable.

Combining these keeps each component focused: mnemonic usability, deterministic account organization, signatures, compact identifiers, and error detection are not interchangeable requirements.

A BRIEF HISTORY

How the pieces arrived

1977–1978 · RSA

Public-key cryptography was publicly introduced by RSA; the famous ACM paper appeared in 1978.

2001–2002 · SHA-2

The SHA-2 family emerged in 2001; NIST's FIPS 180-2 formalized SHA-256/384/512 in 2002.

2012 · BIP-32

Hierarchical deterministic wallets and extended keys.

2013 · BIP-39

Mnemonic code for deterministic wallet seeds.

2014 · BIP-44

A multi-account hierarchy and standard derivation path.

2015 · SHA-3

NIST standardized SHA-3 in FIPS 202, based on the Keccak design.

2016 · EIP-55

Ethereum's mixed-case checksum address encoding was proposed.

Across the pipeline

secp256k1 is the curve; it is a separate public-key primitive, not a hash standard.

Date nuance: SHA-2 is often placed at 2001 in summaries; the formal NIST approval of FIPS 180-2, including SHA-512, was announced on 26 August 2002. RSA is associated with 1977; its journal paper was published the following year.

STATISTICAL PROPERTIES

Random-looking is not the same as random

  • Mnemonic and seed: security starts with unpredictable entropy. The checksum restricts valid mnemonic strings; the 512-bit seed is a deterministic KDF output, not 512 bits of new entropy.
  • Derived keys: BIP-32 child keys are deterministic values under the seed and path. They should be difficult to predict without the parent secret, but observing one wallet's few addresses is not a meaningful randomness test.
  • Curve points: public keys lie on secp256k1's group, so their coordinates are constrained. Valid points are not uniform over all 256-bit coordinate pairs; the point generation operation reflects the chosen secret and group structure.
  • Addresses: truncating Keccak-256 to 160 bits is intended to make outputs look uniform and to resist preimage/collision attacks. A histogram from a handful of addresses cannot establish those security properties.
  • EIP-55 case pattern: capitalization is deterministic from the address's lowercase text and its Keccak hash. It adds error detection, not entropy or secrecy.

Hash functions are designed for avalanche-like sensitivity: a small input change should change many output bits unpredictably. Scalar multiplication has different structure and purpose. Neither a visual pattern nor a small statistical sample proves cryptographic strength; that rests on the primitive's design, parameters, analysis, and implementation.
